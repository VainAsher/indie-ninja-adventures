## Feature 1: Custom Launcher

A separate buildable exe (`ninja_dash_launcher.exe`) that:
- Shows a tkinter GUI window
- Reads local game version from `version.json` next to the exe
- Checks the GitHub releases API for a newer version
- Offers to download + SHA256-verify a new release asset
- Shows download progress
- Launches `ninja_dash.exe` (or `python demo_game.py` in dev mode)
- Builds independently via its own PyInstaller spec

### Phase L1 — Core launcher (this session) ✅
- `version.json` — game version schema
- `launcher/__init__.py` — package marker
- `launcher/launcher.py` — tkinter UI + GitHub API + download + launch
- `build/ninja_dash_launcher.spec` — onefile PyInstaller spec
- `build/build.py` — extended with `--launcher` flag

### Phase L2 — Update UX (follow-up)
- Atomic update: download to temp, rename on success, keep backup
- `update.bat` relay for in-place exe replacement on Windows
- macOS/Linux paths
- Zip distribution (extract alongside exe rather than replace)

### Phase L3 — Mod browser (future)
- Browse/install mods from GitHub releases tagged `mod-*`
- Checksum verification per mod asset
- Enable/disable toggles passed as `--mods` args to game

## Feature 2: Multiplayer Networking Foundation

Architecture: authoritative server, lockstep inputs, TCP with length-prefixed JSON frames.

### Why these design choices
- **TCP not UDP**: reliability is more important than raw latency for a 60Hz turn-based-feeling platformer. UDP adds complexity (packet ordering, acks) that Phase 1 doesn't need.
- **asyncio in background thread**: the pygame main loop is synchronous. asyncio runs in a daemon thread; communication uses `queue.Queue` (thread-safe, no asyncio primitives in the pygame side).
- **Relay server for Phase 1**: the server does not run a game simulation yet. It stores the latest input from each connected client and broadcasts a state packet back. Full authoritative simulation is Phase 2.

### Protocol: length-prefixed JSON
```
[4 bytes big-endian uint32: payload length][UTF-8 JSON body]
```

Message types (client → server): `client_hello`, `input`
Message types (server → client): `server_hello`, `server_state`, `player_join`, `player_leave`, `error`

### Phase N1 — Wire format + snapshots (this session) ✅
- `network/protocol.py` — `Message`, `encode_message`, `read_message`, `write_message`
- `network/snapshots.py` — add `PlayerState` + `MultiplayerSnapshot` (Snapshot unchanged)

### Phase N2 — Server + client (this session) ✅
- `network/server.py` — asyncio TCP server, `GameSession`, `GameServer`, `run_server()`
- `network/client.py` — `NetworkClient` with thread-safe send/recv queues

### Phase N3 — CLI integration (this session) ✅
- `demo_game.py` — `--host <port>` and `--connect <host:port>` args
- Server thread started if `--host`; client thread started and connected if `--connect`
- Each frame: client sends `InputCommand`; server echoes `ServerState` back

### Phase N4 — Authoritative simulation (follow-up, large)
Requires extracting the game loop from `demo_game.py` into a headless-runnable
`game/game_runner.py` class. Server runs that loop; clients send inputs; server
broadcasts authoritative positions; clients reconcile.

### Phase N5 — Full sync + polish (follow-up)
- Input buffering and rollback on client
- Latency compensation (interpolation)
- Lobby/matchmaking UI
- Network stats HUD (ping, frame delta)
- Reconnection logic
