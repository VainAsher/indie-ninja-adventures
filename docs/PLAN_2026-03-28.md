## 4. Reported Bugs (Player-Observed, March 2026)

Six bugs were reported in this session. Investigation findings are below.

### Bug 1 — Sprite rotates/flips during attack

**Location**: [demo_game.py](../demo_game.py) ~L2898–2907, [rendering/animation_system.py](../rendering/animation_system.py)

**Root cause (likely)**: During an attack the player's `state.facing` can update from input handling mid-animation, causing the pre-flipped frame cache to switch direction frame-to-frame. Additionally, the wall-contact sprite inversion (`sprite_facing = -sprite_facing` when on a wall) can fire unintentionally during an attack that makes contact with a wall.

**Fix needed**: Lock `sprite_facing` to the value at attack start and hold it for the full attack animation duration. Disable the wall-inversion path while an attack is active.

### Bug 2 — Hurt and death animations don't play fully

**Location**: [rendering/animation_system.py](../rendering/animation_system.py) L84–86, [demo_game.py](../demo_game.py) L173–177, [game/health_system.py](../game/health_system.py)

**Root cause (certain)**: `hurt` animation is 3 frames at 12 fps = 0.25 s. Invincibility frames are 60 ticks = 1.0 s. The animation finishes and freezes on its last frame for the remaining 0.75 s. For death, the game likely resets or transitions scene before the 5-frame death animation finishes.

**Fix needed**: Either loop the hurt animation while i-frames are active, or reduce i-frame duration to match animation length. For death, block scene transitions until the death animation completes.

### Bug 3 — Jump animation frame assignment

**Location**: [rendering/animation_system.py](../rendering/animation_system.py) L76–77, L359–363, [demo_game.py](../demo_game.py) L204–213

**Root cause (likely)**: The sprite sheet's frame order may be inverted relative to the code expectation. The code extracts `raw[0]` for "jump" (ascending) and `raw[1]` for "fall" (descending). If the artist placed the falling pose first in the sheet, these are swapped.

**Fix needed**: Confirm sprite sheet frame order vs code. Either swap the extraction indices (`raw[1]` → jump, `raw[0]` → fall) or reorder the sprite sheet.

### Bug 4 — Victory/mission complete screen never triggers

**Location**: [demo_game.py](../demo_game.py) L2414–2526, [game/objective_tracker.py](../game/objective_tracker.py) L464–465, [game/mission_manager.py](../game/mission_manager.py)

**Root cause (certain)**: `level_complete` is only set in campaign mode when the player reaches the exit portal AND `mission_manager.exit_locked == False`. The `objective_tracker` is meant to call `mission_manager.unlock_exit()` when all objectives complete, but this wiring is either missing or broken — meaning the exit never unlocks, the portal is never passable, and the victory screen never renders.

**Fix needed**: Trace and repair the chain: `objective_tracker._on_objective_complete()` → check all objectives → call `mission_manager.unlock_exit()` → player hits exit → `level_complete = True` → victory screen renders.

### Bug 5 — Respawn without full health

**Location**: [entities/player.py](../entities/player.py) L448, [demo_game.py](../demo_game.py) ~L2156/2385/2521

**Root cause (likely)**: `player.reset()` correctly sets `current_hp = max_hp`, but the actual respawn code path in `demo_game.py` may not call `reset()` — it may only reposition the player without restoring health.

**Fix needed**: Confirm every respawn code path in `demo_game.py` calls `player.reset(spawn_x, spawn_y)` rather than just setting position directly.

### Bug 6 — Mission completion doesn't unlock further missions

**Location**: [game/mission_manager.py](../game/mission_manager.py) L363–409, [game/campaign_manager.py](../game/campaign_manager.py) L113–150, [demo_game.py](../demo_game.py) L2449–2467

**Root cause (certain)**: `mission_manager.complete_mission()` marks the mission as COMPLETED and saves to `campaign.completed_missions`, but nothing calls `campaign_manager` to evaluate which missions or regions should now unlock. `campaign_manager.can_unlock_region()` exists as a check function only — `unlock_region()` is never called automatically after completion.

**Fix needed**: After mission completion is recorded, iterate mission/region unlock conditions in `campaign_manager` and unlock anything whose requirements are now satisfied. Wire this into the `MissionCompleteEvent` handler or into the post-exit flow in `demo_game.py`.

## 5. Proposed Work Plan

Work is organized in priority order. Phase 0 (bug fixes) must come first — the campaign loop is broken without it. Each phase follows the work loop (plan → tasks → commit each unit → update plan → push).

---

### Phase 0: Bug Fixes — Playable Campaign Loop

**Goal**: Fix the three P0 bugs and two P1 animation bugs before anything else. The campaign is broken without these.

**Tasks**:

1. Trace and repair objective → mission_manager.unlock_exit() → level_complete chain (Bug 4)
2. After mission save, call campaign_manager unlock evaluation to unlock subsequent missions/regions (Bug 6)
3. Confirm every death/respawn path calls player.reset() to restore full health (Bug 5)
4. Fix hurt animation: loop while i-frames active, or block state exit until animation completes (Bug 2)
5. Fix death animation: block scene transition until death animation completes (Bug 2)
6. Lock sprite_facing at attack start; disable wall-inversion during active attack (Bug 1)
7. Confirm jumpfall sprite sheet frame order vs code indices; swap if needed (Bug 3)
8. Run full test suite; run UAT cases UAT-BOOT-002, UAT-COMBAT-001, UAT-COMBAT-002 to verify

**Exit criteria**: Player can complete a mission → victory screen shows → next mission is selectable. Player dies → respawns at full health. Animations play correctly for hurt, death, jump, and attack.

**Commit strategy**: One commit per bug fix group (progression chain, health, animations).

### Phase 2: Boss Integration — M1 Core

**Goal**: Make boss encounters reachable and playable in at least one mission.

**Context**: boss.py, boss_ai.py, and boss_manager.py are fully implemented with six boss types (SHADOW_LORD, FIRE_DEMON, ICE_QUEEN, NECROMANCER, DRAGON, VEIL_MAIDEN). Nothing calls them.

**Tasks**:
1. Wire BossManager into game_initialization.py alongside EnemyManager
2. Wire boss update/render loop into demo_game.py play loop
3. Add `boss` field to at least one mission in data/missions.json per region (6 missions)
4. Wire objective_tracker to detect boss death as mission completion condition
5. Wire ability_gate.py into hub world generation (gate one ability per region)
6. Add tests: boss_manager spawns on boss room type, ability gate blocks/unlocks correctly

**Exit criteria**: Can start a campaign mission and encounter + defeat a boss. Ability gate blocks progress without the required ability.

**Commit strategy**: game_initialization wiring → demo_game loop → missions.json data → ability gate → tests.

### Phase 3: Audio Foundation — M2 Core Gap

**Goal**: Wire pygame.mixer so that sound effects play in-game and volume settings do something.

**Context**: config/settings.py has `music_volume` and `sfx_volume`; game_initialization.py loads settings; no mixer calls exist anywhere in the runtime path.

**Scope decision**: SFX only. Music/soundtrack wiring deferred to backlog (revisit after SFX is stable).

**Tasks**:

1. Initialize pygame.mixer in game_initialization.py; wire sfx_volume from settings
2. Add an AudioManager class (or small module) with play_sfx(name); silent fallback if asset missing
3. Wire combat SFX hooks: attack swing, enemy hit, player hurt, player death
4. Wire environment SFX hooks: jump, land, dash, pickup coin, open door
5. Wire UI SFX hooks: menu select, menu confirm, inventory open/close
6. Wire settings menu sfx_volume slider to AudioManager volume
7. Document expected audio asset filenames in assets/audio/README or similar

**Exit criteria**: SFX volume slider in settings changes audible volume. Combat + movement SFX play if asset files are present. No crash if assets are missing.

**Commit strategy**: AudioManager + initialization → combat hooks → env/UI hooks → settings wiring.

---

### Phase 4: Settings Wiring — M3 Foundation

**Goal**: Wire config/settings.py into the live input and display path so the settings menu controls real behavior.

**Context**: Key bindings and display options (fullscreen, vsync, show_hitboxes) are defined in settings but hardcoded in player.py and game_initialization.py.

**Tasks**:
1. Replace hardcoded key constants in player.py and demo_game.py with lookups from settings
2. Wire `fullscreen` and `vsync` from settings into display init / settings menu toggle
3. Wire `show_hitboxes` from settings into collision debug rendering in demo_game.py
4. Wire `screen_shake` toggle from settings into camera_system.py shake calls
5. Ensure settings persist on write (save_system or JSON write) and reload on startup
6. Add tests: settings toggle changes runtime behavior, persist and reload correctly

**Exit criteria**: Changing a key binding in the settings menu takes effect in-game. Fullscreen toggle works. Hitbox toggle works.

**Commit strategy**: Input binding → display options → debug toggles → persistence tests.
